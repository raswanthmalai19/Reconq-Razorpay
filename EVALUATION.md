# EVALUATION.md

## Methodology

1. `data/generate_data.py` produces a seeded (`random.seed(42)`) synthetic settlement report, internal ledger, and a held-out `ground_truth.csv` across 8 labeled mismatch classes. The matching engine never reads `ground_truth.csv` at inference time — it exists only for scoring.
2. `engine/train.py` builds candidate pairs from bucketing, self-labels them from ground truth (true pair = positive, every other same-bucket pair = hard negative), and trains a `LogisticRegression` on a 60/20/20 stratified train/val/test split.
3. `eval/harness.py` runs the full pipeline twice against the identical trained model — once with the risk-weighted (amount-banded) policy, once with the naive fixed-0.85-threshold baseline — and scores both against `ground_truth.csv`.
4. Every metric in `eval/report.md` is computed by this run; nothing is hand-entered.

## Reproducing the numbers

```bash
python data/generate_data.py
python eval/harness.py
cat eval/report.md
```

Because generation is seeded, re-running on a clean clone reproduces the same dataset and (subject to `LogisticRegression`'s own internal determinism at fixed `random_state=42`) the same metrics.

## Metric definitions

- **Match precision** — of everything `AUTO_MATCHED`, the fraction that is an actual true pair per ground truth.
- **Match recall** — of all true pairs in ground truth, the fraction found at any status (`AUTO_MATCHED` or `HUMAN_REVIEW`).
- **False-match rate** — `AUTO_MATCHED` pairs that are not true pairs. The most consequential number: it means money would be reconciled against the wrong invoice.
- **Human-review rate** — the fraction of decided pairs routed to a human. Read alongside false-match rate, not alone — the risk-weighted design deliberately accepts a higher review rate on high-value transactions in exchange for a lower false-match rate there.
- **Signature-moment count** — the number of (settlement, ledger) pairs where the risk-weighted policy and the naive baseline reach a *different* final status at the *identical* confidence score, purely because of transaction amount. This is the concrete, checkable evidence for the core product claim.

## Honest reporting

`eval/report.md`'s "Known Failure Modes" section is generated by the harness itself, not hand-written, and lists any measured metric that misses its pre-declared target — currently: false-match rate (1.5% measured vs. <1% target) and a validation/test accuracy gap plausibly attributable to small split size at this dataset scale. Neither is hidden or rounded away.

## What was NOT evaluated

- Real settlement data (synthetic only).
- Production-scale throughput (only a 154-record set was run; a larger stress-test pass is named as future work in `RECONQ_MASTER_SPEC.md`, not claimed as done).
- Split/merge groups larger than 4 members (capped by design; falls safely to `UNRESOLVED`).
- LLM explanation quality at scale beyond manual spot-checking during development.
